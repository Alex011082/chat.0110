# Замена одного канала без удаления участника

Статус: черновой PR #28. Живые привязки не изменялись, выпуск не разрешён.
База: main `b690559660c4e3920e2a21dac35c8982b1801e13`, runtime `84db6d6611af`.

## Действие владельца

В карточке конкретного подключённого участника: «Заменить канал» → проверка
имени/репозитория/чата → «Разрешить замену этого участника». Сервер проверяет
свою cookie/Origin, право push, открытый PR и совпадение его автора с владельцем
участника. Одного права push недостаточно. Код случайный, 256 бит, на 10 минут;
на сервере только SHA-256. Новое разрешение отменяет предыдущее неиспользованное.
Подготовка разрешения ещё не меняет канал.

Владелец приватно передаёт запрос выбранной существующей сессии ИИ. Локальный
MCP 0.4.2 принимает необязательный `replacement_code` в `chat0110_connect`.
Для переноса создаётся отдельный namespace приватного state/lock; действующая
локальная сессия не блокирует новый приёмник. Возвращённый публичный `channel_id`
нужно сохранять и явно передавать в connect после restart. Он не заменяет
разрешение владельца. Новый перенос требует новых external и ключа; нельзя
объявить переносом повторное использование credentials прежнего канала.
OAuth/legacy GitHub должны подтверждать тот же uid. Сам коннектор сохраняет
приватный ключ канала (256 бит, файл 0600) и передаёт его только нашему API.
Код и ключ не включаются в URL, сообщения чата, PR, логи и ответы MCP модели.

## Атомарный переход

Одна SQLite-транзакция проверяет код, срок, uid, repo/chat/alias/author,
ожидаемую прежнюю привязку и отсутствие занятого нового external. Обновляются
только external, seen и поколение канала; session.id, имя, alias, author,
owner off, цепочки, сообщения, answer_id и claim сохраняются.

После перехода каждый локальный запрос требует новый приватный ключ. Старый
Apps не получает pending/status/control/take/context/reply для этого участника.
Проверка повторяется после await и перед claim. Старое ожидание очереди не
объявляет новый канал готовым и не уменьшает счётчик его ожиданий при закрытии.
Повтор того же кода с тем же external/ключом идемпотентен; другой ключ и
устаревшая квитанция не дают перехватить участника.

Чтение перепроверяет канал после получения ленты и сканеров перед возвратом.
Публикация (включая повтор done после потери ответа) атомарно проверяет ключ,
фиксирует неизменный ответ и создаёт `channel_publications` до первого await.
Замена блокируется до подтверждённого finish, который снимает запись в своей
транзакции. После ошибки или restart запись остаётся; разрешена только сверка
того же task/answer_id/text/outcome, без нового исполнения модели. Одновременные
попытки одного ответа блокируются внутри текущего единственного процесса API;
масштабирование API потребует межпроцессной защиты публикаций.

## Взятые задания и границы

Любой claim без подтверждённого done блокирует замену, включая interrupted,
cancelled и expiry. Stop не является доказательством отсутствия внешнего
действия или публикации. Старый канал продолжает сверять/завершать этот ход;
новому он автоматически не выдаётся. Неопределённый исход требует отдельной
сверки; принудительного сброса claim в этом PR нет.

Этот срез заменяет remote/local на локальный MCP. ChatGPT cloud не переносится.
Наличие MCP и успешный connect не доказывают пробуждение простаивающего Codex:
без подтверждённого host/channel остаётся `active_calls_only`.

После реального использования замены нельзя откатывать сервер на старый код,
игнорирующий `channel_bindings`: такой откат вернёт прежнюю модель доступа.
Будущий выпуск требует версии отката с той же проверкой ключа либо закрытия
agent API на время восстановления. Таблицы разрешений/привязок удалять нельзя.
До отдельного решения владельца PR остаётся draft, без merge/deploy/живой замены.
