# Концепция Fork — записка владельца, 23.10.2026

Вот теперь у нас появляется **не просто групповой чат с ИИ, а система, которая сохраняет историю развития идей и позволяет перемещаться по ней как по дереву Git**.

И кнопка **Fork** здесь становится одной из главных функций продукта `Chat.0.1.1.0`.

Причём я бы сохранил твою терминологию: не «создать дочерний чат», а именно **Fork**. Потому что это гораздо точнее описывает действие.

## 1. Как будет работать Fork

Представим, что мы обсуждаем RoboChain.

В чате уже 150 сообщений. На сообщении №87 Claude предлагает альтернативную конструкцию манипулятора.

Ты нажимаешь **Fork** непосредственно на этом сообщении.

Система:

1. Сохраняет точку ветвления — конкретное сообщение, GitHub commit SHA и состояние обсуждения.
2. Создаёт новую ветку `chat/robochain/manipulator-v2`.
3. Создаёт новый PR с собственным потоком комментариев.
4. Переносит в контекст дочернего чата историю родительского обсуждения до точки ветвления.
5. Открывает новый чат, где ты продолжаешь обсуждение альтернативы.

При этом первоначальная беседа остаётся нетронутой.

**Ключевой момент:** дочерний чат наследует контекст родителя до выбранной точки, но не должен автоматически наследовать все будущие сообщения родителя.

Иначе это уже не настоящее ветвление.

## 2. Как я представляю визуализацию

На сайте будет отдельный экран **Conversation Graph** — интерактивная карта обсуждений.

Например:

Это не просто схема веток.

Каждая точка — реальное сообщение, решение или зафиксированное состояние.

Нажимаешь на неё — открывается соответствующее место переписки.

### Три режима просмотра

**Chat View** — обычный интерфейс переписки с несколькими ИИ.

**Tree View** — дерево всех разговоров, дочерних веток и ответвлений.

**Timeline View** — хронология развития идеи: кто что предложил, когда создали Fork, какие решения приняли.

Я бы также предусмотрел **Decision View** — отдельный режим, показывающий только принятые решения, отклонённые варианты и аргументы.

## 3. Самая интересная функция — возврат из Fork

Допустим, в основном чате мы выбрали вакуумные руки.

Параллельно в Fork Claude исследует механическую платформу.

Спустя два дня ты открываешь дочернюю ветку и видишь, что предложенный механизм оказался лучше.

Ты нажимаешь:

**«Вернуть решение в родительский чат»**

Система не сливает автоматически все сообщения, а формирует предложение:

> В дочернем чате исследована альтернативная система передачи коробок. По предварительным расчётам она обеспечивает более высокую пропускную способность. Предлагается пересмотреть решение №12.

К предложению прикрепляются ссылки на сообщения, доказательства и коммиты.

В родительском чате появляется сообщение со ссылкой на Fork.

Ты можешь принять предложение, отклонить его или отправить на дополнительное обсуждение.

Это фактически **Pull Request для идеи**.

Причём, в отличие от обычного Git merge, здесь нужно учитывать смысловые противоречия, а не только изменения файлов.

## 4. Git-коммит как точка фиксации

Здесь я бы заложил важное различие.

Комментарии PR в GitHub не являются частью истории Git-коммитов.

Поэтому для твоего требования «вернуться точно к тому месту, где мы отделились» необходимо сохранять три идентификатора:

| Идентификатор | Для чего нужен |
|---|---|
| `parent_pr` | Из какого чата произошёл Fork |
| `parent_message_id` | На каком сообщении произошло ветвление |
| `fork_commit_sha` | Какое состояние файлов и контекста было зафиксировано |

Например:

```json
{
  "chat_id": "robochain-manipulator-v2",
  "parent_chat_id": "robochain",
  "parent_pr": 12,
  "parent_message_id": 874,
  "fork_commit_sha": "a3f8c91",
  "fork_type": "alternative_solution",
  "created_by": "alex"
}
```

Именно эта комбинация позволит точно восстанавливать происхождение обсуждения.

При этом для полного восстановления контекста на момент ветвления нужно сохранять снапшот или границу истории, поскольку комментарии PR могут изменяться независимо от Git.

## 5. А теперь представь масштаб

Через год у тебя сотни чатов.

Например, ты обсуждал YTNG, затем из этого разговора появилась идея второго мнения переводов.

Из неё — идея независимых арбитров.

Затем — исследование локальных моделей.

Потом — эксперименты с распределёнными агентами.

Обычно связь между этими обсуждениями теряется.

**В Chat.0.1.1.0 ты сможешь открыть первоначальную идею и увидеть всё дерево её развития.**

Но я бы предусмотрел два типа связи:

**Fork** — дочерний разговор, происходящий из конкретного сообщения родителя.

**Link** — смысловая связь между двумя независимыми разговорами.

Например, идея из YTNG оказалась полезной для HR0110. Не нужно делать один проект дочерним по отношению к другому. Достаточно связать их.

Так мы получим не только дерево, но и полноценный **граф знаний и решений**.

## 6. Что я считаю особенно важным

Нужно сохранить возможность создавать Fork **не только из целого чата, но и из любого отдельного сообщения**.

Например, ты выделяешь мой ответ о роботах и нажимаешь Fork.

Новый разговор начинается именно с этой точки.

Причём система должна зафиксировать:

- Кто высказал исходную идею.
- Когда это произошло.
- В каком чате.
- Какие сообщения предшествовали.
- Какое состояние обсуждения было на тот момент.
- Какие агенты участвовали.

А затем отображать всё это в интерактивном графе.

## 7. Архитектурное решение, которое я бы зафиксировал

**GitHub остаётся основным источником данных.**

Ветки — организация разговоров и фиксация их состояния.

PR — потоки сообщений.

Коммиты — снимки решений и контекста.

Метаданные Fork — связи между разговорами.

GitHub API и Webhooks — синхронизация интерфейса.

Для быстрого поиска и отрисовки графа можно использовать локальный индекс, но он будет восстанавливаемым из GitHub, а не отдельным независимым источником истины.

### И самое главное

Я бы добавил в визуализацию ещё одну функцию:

**«Показать путь идеи».**

Ты открываешь любой результат, например готовую спецификацию RoboChain.

Нажимаешь «Показать происхождение».

И система подсвечивает всю цепочку:

**Первоначальная идея → обсуждение → Fork → альтернативная гипотеза → эксперимент → принятое решение → спецификация.**

С возможностью открыть любое исходное сообщение.

Это уже не просто история переписки. Это **прослеживаемая история формирования решений** — своего рода Git для коллективного мышления человека и ИИ.

Именно такую архитектуру я бы закладывал в `Chat.0.1.1.0` с самого начала.
