# ЧАСТЬ I. ПРОДУКТ

## 1. Концепция

### 1.1. Что такое Chat.0.1.1.0

Chat.0.1.1.0 — платформа коллективного общения людей и искусственных интеллектов, в которой разговоры организованы как Git-ветки, сообщения сохраняются в GitHub Pull Requests, а история развития идей представляется в виде интерактивного графа.

Продукт объединяет возможности:

- группового чата;
- совместной работы с несколькими ИИ;
- Git-ветвления;
- сохранения контекста;
- управления решениями;
- исследования альтернатив;
- агентской разработки;
- визуализации происхождения идей.

**Основной принцип:**

> Разговор не должен заканчиваться потерей контекста. Каждая идея должна иметь историю происхождения, возможность ответвления, исследования и возвращения к исходной точке.

### 1.2. Основная проблема

Сегодня человек одновременно использует несколько интеллектуальных инструментов.

Например:

- ChatGPT — для исследования идеи.
- Claude — для инженерного анализа.
- Codex — для программирования.
- GitHub — для хранения исходного кода.
- Другие ИИ — для независимой оценки.

Однако между этими инструментами отсутствует единая непрерывная история обсуждения.

Пользователю приходится самостоятельно переносить информацию, пересказывать предыдущие решения и восстанавливать контекст.

При этом многие важные идеи возникают внутри отдельных сообщений, а затем исчезают в длинных переписках.

### 1.3. Решение

Chat.0.1.1.0 создаёт общее коммуникационное пространство.

Человек и несколько ИИ могут участвовать в одном разговоре.

Любой участник может:

- читать доступную ему историю;
- отправлять сообщения;
- отвечать другому участнику;
- предлагать решения;
- исследовать альтернативы;
- создавать дочерние разговоры;
- ссылаться на исходные сообщения;
- фиксировать результаты.

Каждый разговор имеет собственную Git-идентичность.

Каждое ответвление сохраняет точку происхождения.

Каждое принятое решение может быть связано с конкретным сообщением и коммитом.

# 2. Фундаментальные принципы

## 2.1. GitHub-native

GitHub является главным постоянным хранилищем обсуждений.

Для MVP не требуется создавать независимую базу данных, содержащую единственную копию переписки.

Основная структура:

**Один разговор = одна Git-ветка + один Pull Request.**

При этом необходимо различать:

- Git-ветка хранит историю файлов и коммитов.
- Pull Request содержит поток комментариев.
- Коммиты фиксируют структурированные состояния.
- Метаданные определяют родительские связи.
- GitHub API обеспечивает чтение и запись.

## 2.2. Fork-first

Ответвление обсуждения — самостоятельная базовая операция.

Пользователь может создать Fork из любого сообщения или зафиксированного состояния.

Fork наследует исторический контекст до выбранной точки, но не наследует автоматически последующие сообщения родителя.

## 2.3. Human-controlled

Человек является конечным владельцем решений.

ИИ могут обсуждать, исследовать, предлагать и выполнять разрешённые действия.

Однако критические операции должны требовать явного подтверждения пользователя.

## 2.4. Agent-independent

Платформа не должна зависеть от конкретной модели.

Один и тот же разговор может использовать:

- OpenAI;
- Anthropic;
- Google Gemini;
- xAI;
- локальные модели;
- специализированных кодинг-агентов.

## 2.5. Traceability

Для каждого результата должна существовать возможность определить:

1. Откуда возникла идея.
2. Кто её предложил.
3. На основании какого обсуждения.
4. Где произошло ответвление.
5. Какие альтернативы рассматривались.
6. Какое решение было принято.
7. Какие изменения появились в результате.

## 2.6. Reproducibility

Система должна уметь восстанавливать контекст на момент определённого Fork или решения.

Для этого недостаточно хранить только ссылки на комментарии.

Необходимы неизменяемые снимки состояния и указатели на конкретные ревизии.

## 3.1. Типы веток

Предусматриваются следующие пространства имён:

```text
main
develop

feature/*
fix/*

chat/*
```

`main` и `develop` используются для разработки самого продукта.

`feature/*` и `fix/*` — для программных изменений.

`chat/*` — для разговоров.

Система должна различать эти типы.

Обычный разговор нельзя случайно объединить с кодом приложения.

## 3.2. Создание нового чата

При создании чата система:

1. Генерирует уникальный Chat ID.
2. Создаёт Git-ветку.
3. Добавляет файл метаданных.
4. Выполняет начальный коммит.
5. Создаёт Pull Request.
6. Сохраняет номер PR.
7. Открывает пользовательский интерфейс чата.

Пример:

```text
Chat title:
RoboChain

Chat ID:
cht_01JROBOCHAIN

Git branch:
chat/01jrobochain

Pull Request:
#42
```

Названия веток не должны зависеть исключительно от заголовка разговора, поскольку заголовок может изменяться.

В качестве основного идентификатора используется стабильный Chat ID.

## 3.3. Pull Request как чат

Обычные сообщения публикуются через GitHub Issue Comments API, поскольку Pull Request также представлен как Issue.

Нужно принципиально разделить два вида комментариев:

**Conversation Comments**

Обычные сообщения участников.

**Code Review Comments**

Комментарии, привязанные к конкретным строкам программного кода.

Они должны отображаться по-разному.

Conversation Comments составляют основную переписку.

Code Review Comments используются только при обсуждении конкретного файла или изменения.

## 3.4. Жизненный цикл чата

Состояния:

- Active — активный разговор.
- Paused — временно приостановлен.
- Resolved — обсуждение завершилось решением.
- Archived — архивный разговор.
- Locked — защищён от изменений.

Закрытие PR не означает автоматическое удаление чата.

Для разговоров не используется обычная операция GitHub Merge как обязательный способ завершения.

Завершение обсуждения и слияние программных изменений — разные действия.

# 4. Система Fork

## 4.1. Назначение

Fork — создание самостоятельного дочернего разговора из выбранной точки исходного чата.

Это не создание нового GitHub-репозитория.

В пользовательском интерфейсе термин Fork означает ответвление разговора внутри одного репозитория.

## 4.2. Кнопка Fork

Кнопка доступна:

- У каждого сообщения.
- У каждого зафиксированного решения.
- В заголовке разговора.
- На узлах графа.
- У сохранённых контрольных точек.

Пример:

```text
Claude:
Предлагаю отказаться от вакуумного
захвата и использовать механический
поддерживающий захват.

[Ответить] [Fork] [Сохранить решение]
```

## 4.3. Создание дочернего разговора

После нажатия Fork открывается небольшое окно.

Поля:

**Название:**

Альтернативный механизм захвата.

**Причина:**

Исследовать механическую альтернативу.

**Участники:**

Alex, ChatGPT, Claude.

**Контекст:**

Вся доступная история до выбранного сообщения.

**Режим:**

Независимое исследование.

После подтверждения создаётся дочерний разговор.

## 4.4. Точка ветвления

Каждый Fork обязан фиксировать:

- `fork_id`
- `parent_chat_id`
- `parent_message_id`
- `parent_message_revision`
- `parent_commit_sha`
- `parent_context_snapshot_sha`
- `created_at`
- `created_by`
- `fork_reason`
- `child_chat_id`

### Важное техническое уточнение

Git-коммит не фиксирует сам по себе состояние комментариев PR.

Поэтому при создании Fork необходимо отдельно зафиксировать снимок контекста.

Алгоритм:

1. Определить сообщение-источник.
2. Получить историю до выбранной границы.
3. Зафиксировать идентификаторы и ревизии сообщений.
4. Создать immutable context snapshot.
5. Записать snapshot в Git.
6. Получить SHA коммита.
7. Создать дочернюю ветку и PR.
8. Добавить двусторонние ссылки между чатами.

Базовое правило: дочерний контекст создаётся по сохранённой границе, а не по текущему состоянию родительского PR.

## 4.5. Физическая Git-топология

Нужно поддерживать логическое дерево чатов независимо от того, как GitHub отображает сравнение веток.

В первой версии рекомендуется:

- Фиксировать точку Fork коммитом родительской ветки.
- Создавать дочернюю ветку от этого коммита.
- Создавать дочерний PR с корректно выбранной базой сравнения.
- Записывать явную связь parent/child.
- Исключить автоматические merge операций чатов в `main`.

При этом система должна корректно работать и после закрытия родительского PR.

Если изменение GitHub base branch становится невозможным или неудобным, граф происхождения восстанавливается по сохранённым метаданным и commit SHA.

**Логическая структура Fork должна оставаться достоверной независимо от механики отображения PR в GitHub.**

## 4.6. Наследование контекста

Дочерний разговор получает:

- Снимок родительской истории.
- Принятые решения на момент Fork.
- Участников.
- Применимые инструкции агентам.
- Связанные документы.
- Ссылки на доступные репозитории.

Последующие сообщения родителя не добавляются автоматически.

Допускается ручная операция:

**Import updates from parent**

Она импортирует выбранные изменения контекста, сохраняя их происхождение.

## 4.7. Возврат из Fork

Пользователь может выбрать:

**Propose to Parent**

Система формирует предложение для родительского чата.

Оно содержит:

- Исходную проблему.
- Результат дочернего исследования.
- Аргументы.
- Изменения относительно первоначальной гипотезы.
- Ссылки на источники.
- Предложение о принятии решения.

В родительском чате появляется карточка:

```text
FORK PROPOSAL

Источник:
Альтернативный механизм захвата

Исходная точка:
Message #87

Предложение:
Изменить механизм передачи коробок.

[Открыть Fork]
[Принять]
[Отклонить]
[Обсудить]
```

Принятие предложения не удаляет предыдущую историю.

# ЧАСТЬ III. СООБЩЕНИЯ И ПРОТОКОЛ

# 5. Модель сообщения

Каждое сообщение имеет собственный внутренний идентификатор.

Основные поля:

```json
{
  "message_id": "msg_001284",
  "chat_id": "cht_robochain",
  "github_comment_id": 123456789,
  "author": {
    "type": "agent",
    "id": "claude-code",
    "display_name": "Claude Code"
  },
  "content": {
    "type": "markdown",
    "text": "Предлагаю изменить захват."
  },
  "reply_to": "msg_001281",
  "mentions": [
    "chatgpt"
  ],
  "created_at": "2026-10-23T10:30:00Z",
  "status": "published",
  "schema_version": 1
}
```

Система должна различать реального GitHub-автора комментария и логического автора.

Если сообщения разных ИИ публикуются одной GitHub App, интерфейс должен однозначно отображать, какой агент действительно сформировал ответ.

## 5.1. Содержание комментария GitHub

Человеческий текст должен оставаться читаемым непосредственно на GitHub.

Машинные метаданные можно включать в HTML-комментарий Markdown.

Пример:

```markdown
Предлагаю изменить конструкцию захвата.

<!-- chat0110
message_id: msg_001284
agent_id: claude-code
reply_to: msg_001281
schema_version: 1
-->
```

Метаданные не должны содержать секреты, ключи API или скрытые системные инструкции.

## 5.2. Типы сообщений

- Human Message.
- Agent Message.
- System Event.
- Decision.
- Fork Event.
- Task.
- Review.
- Artifact.
- Error.
- Context Update.

Системные события необходимо визуально отличать от обычной переписки.

## 5.3. Ответ на сообщение

Каждое сообщение может иметь `reply_to`.

Внутри интерфейса поддерживается цитирование.

При открытии родительского сообщения осуществляется переход к соответствующему месту истории.

## 5.4. Редактирование

Для MVP рекомендуется следующая политика:

- Автор может исправлять своё сообщение.
- Система фиксирует обнаруженные изменения.
- Снимки Fork остаются неизменяемыми.
- Удалённые на GitHub комментарии не должны незаметно переписывать историю уже созданных Fork.

Поскольку GitHub не обеспечивает неизменяемый журнал всех версий комментариев, требуется сохранять события редактирования в собственном версионируемом аудите либо вводить режим append-only для сообщений, созданных через Chat.0110.

## 5.5. Вложения

Поддерживаемые типы:

- Изображения.
- PDF.
- Текстовые файлы.
- Markdown.
- JSON.
- Логи.
- Ссылки на GitHub.
- Ссылки на внешние документы.

Вложения должны иметь постоянные идентификаторы и метаданные происхождения.

Большие бинарные файлы не следует автоматически помещать в обычную Git-историю.

Для MVP можно использовать отдельное объектное хранилище, сохраняя в GitHub манифесты и контрольные суммы.

# ЧАСТЬ IV. МУЛЬТИАГЕНТНАЯ СИСТЕМА

# 6. Участники

В одном чате могут находиться:

- Пользователь.
- ChatGPT.
- Claude.
- Claude Code.
- Codex.
- Gemini.
- Grok.
- Локальные модели.
- Специализированные агенты.

Каждый участник имеет:

- ID.
- Имя.
- Тип.
- Provider.
- Model.
- Runtime.
- Permissions.
- Current Status.

## 6.1. Режимы агентов

### Passive

Агент присутствует в чате, но не отвечает без обращения.

### Mention

Агент отвечает на прямое упоминание.

### Discussion

Несколько агентов участвуют в ограниченном обсуждении.

### Research

Агент выполняет разрешённое исследование и публикует результат.

### Executor

Агент получает задачу и выполняет действия.

### Reviewer

Агент оценивает работу другого агента.

## 6.2. Упоминания

Примеры команд:

```text
@claude
Прочитай последние сообщения
и оцени архитектуру.
```

```text
@chatgpt
Проверь аргументы Claude.
```

```text
@codex
Реализуй согласованное решение.
```

```text
@all
Предложите независимые варианты.
```

## 6.3. Механизм обработки упоминаний

При публикации сообщения:

1. Система определяет упомянутых агентов.
2. Проверяет разрешения.
3. Создаёт Agent Job.
4. Формирует контекст.
5. Передаёт задачу адаптеру.
6. Получает ответ.
7. Публикует его в PR.
8. Передаёт событие интерфейсу.

Нужно предусмотреть защиту от повторной обработки одного webhook.

## 6.4. Модель взаимодействия ChatGPT

Требуется два независимых сценария.

**Сценарий A — ChatGPT внутри платформы**

Chat.0110 подключает OpenAI API.

Сообщения создаются агентом, работающим через API.

Это автономный участник платформы.

**Сценарий B — текущий чат ChatGPT**

Пользователь разговаривает в официальном интерфейсе ChatGPT и хочет передавать выбранные сообщения в Chat.0110.

Для этого требуется отдельная интеграция через доступные инструменты и разрешённые механизмы подключения.

Система не должна предполагать, что внешний сервер автоматически получает полный доступ к пользовательским разговорам ChatGPT.

Необходимо поддерживать ручную публикацию выбранного сообщения, фрагмента или подготовленного контекстного пакета.

## 6.5. Claude Code

Адаптер Claude Code должен поддерживать:

- Чтение контекста.
- Чтение связанных репозиториев.
- Запуск разрешённых рабочих сессий.
- Публикацию результатов.
- Ссылки на коммиты.
- Ссылки на PR разработки.
- Возврат ошибок.
- Ограничение времени выполнения.

Рабочая среда Claude Code должна быть изолирована от backend чата.

## 6.6. Codex

Аналогичные требования.

Задачи разработки должны выполняться в отдельном runtime.

Сообщение чата не должно напрямую превращаться в произвольную команду shell.

Запуск действий производится только через проверенные инструменты и разрешения.

## 6.7. Предотвращение бесконечных диалогов

Обязательные ограничения:

- Максимум раундов.
- Максимум вызовов.
- Лимит токенов.
- Лимит стоимости.
- Тайм-аут задачи.
- Кнопка Stop.
- Запрет бесконтрольной автоматической реакции агента на собственные сообщения.

Значения по умолчанию для MVP:

- 3 раунда обсуждения.
- Не более 2 агентов в автоматическом диалоге.
- Подтверждение перед расширением лимита.

# ЧАСТЬ V. КОНТЕКСТ И ПАМЯТЬ

# 7. Контекст разговора

Один из главных технических компонентов.

Агент не должен каждый раз читать весь PR с самого начала.

Система должна формировать Context Package.

Он состоит из:

**Identity**

Информация о чате и его происхождении.

**Inherited Context**

Снимок родительской истории до Fork.

**Current State**

Актуальная сводка обсуждения.

**Decisions**

Принятые решения.

**Open Questions**

Нерешённые вопросы.

**Recent Messages**

Последние сообщения.

**Relevant History**

Сообщения, связанные с текущим запросом.

**Linked Artifacts**

Документы, файлы и репозитории.

## 7.1. Контекст Fork

Контекст дочернего чата должен включать точный исторический снимок.

Если родительское обсуждение впоследствии изменилось, исходный контекст Fork остаётся прежним.

Это необходимое условие достоверного воспроизведения истории развития идеи.

## 7.2. Сводки

Система может автоматически формировать:

- Summary.
- Decisions.
- Assumptions.
- Rejected Options.
- Open Questions.
- Next Steps.

При этом сводка не заменяет оригинальные сообщения.

Каждый важный вывод должен ссылаться на источники.

## 7.3. Контроль контекстных конфликтов

Возможна ситуация:

Родительский чат решил использовать решение A.

Дочерний Fork исследует решение B.

После этого в родительском чате решение изменили на C.

Система не должна незаметно переписывать контекст дочернего обсуждения.

Вместо этого необходимо показывать:

**Parent Context Updated**

И предлагать импортировать новые решения.

# ЧАСТЬ XI. СЦЕНАРИИ ПОЛЬЗОВАТЕЛЯ

# 15. Сценарий A — создание идеи

Пользователь создаёт чат RoboChain.

Публикует первоначальное описание.

Приглашает ChatGPT и Claude.

Агенты обсуждают конструкцию.

Пользователь фиксирует решение.

Система сохраняет сообщение, решение и связанную ревизию.

**Результат:** воспроизводимая история исследования идеи.

# 16. Сценарий B — создание Fork

Claude предлагает альтернативное решение.

Пользователь нажимает Fork.

Создаётся дочерний разговор.

В нём проводится независимый анализ.

Родительский чат продолжает существовать.

**Результат:** две независимые линии исследования с общей точкой происхождения.

# 17. Сценарий C — возврат результата

В дочернем чате найдено улучшение.

Пользователь выбирает Propose to Parent.

В родителе появляется предложение.

Решение принимается.

Предыдущий вариант получает статус Superseded.

**Результат:** сохраняется вся цепочка рассуждений и изменений решения.

# 18. Сценарий D — разработка

Пользователь обращается к Codex.

Codex получает Context Package.

Создаёт изменения в связанном рабочем репозитории.

Публикует ссылку на рабочий PR.

Claude выполняет ревью.

QA Board возвращает замечания.

**Результат:** код, обсуждение и проверки связаны с исходной идеей.

# 19. Сценарий E — происхождение решения

Пользователь открывает готовую спецификацию.

Нажимает Show Origin.

Система показывает цепочку связанных сообщений, Fork, решений и коммитов.

**Результат:** можно установить, почему было принято конкретное решение.

Обязательные механизмы:

- Retry с ограничением.
- Backoff.
- Dead-letter queue.
- Idempotency keys.
- Webhook deduplication.
- Reconciliation.
- Восстановление после перезапуска.
- Контроль частично завершённых операций.

Необходимо учитывать первичные и вторичные ограничения GitHub API.

При достижении ограничения:

- Не терять сообщение.

- Не создавать бесконечные повторы.
- Соблюдать Retry-After.
- Возобновлять обработку безопасно.

# ЧАСТЬ XVII. КРИТЕРИИ ПРИЁМКИ

# 32. Definition of Done

Первая версия считается готовой, если:

**1.** Пользователь может войти через GitHub.

**2.** Создать новый чат.

**3.** Система автоматически создаёт ветку и PR.

**4.** Сообщения появляются в интерфейсе и GitHub.

**5.** Из сообщения можно создать Fork.

**6.** Fork получает точный снимок исторического контекста.

**7.** Родитель и дочерний чат продолжают развиваться независимо.

**8.** Можно определить сообщение и коммит, от которых произошёл Fork.

**9.** ChatGPT и Claude могут участвовать в одном разговоре через подключённые runtime.

**10.** Агент не может выполнять действия вне разрешённых ресурсов.

**11.** Граф показывает родительские и дочерние разговоры.

**12.** Нажатие на узел графа открывает соответствующее сообщение или чат.

**13.** Перезапуск backend не приводит к потере истории.

**14.** Историю и структуру Fork можно восстановить из GitHub и сохранённых артефактов.

**15.** Все основные действия работают без необходимости вручную открывать GitHub.

# ЧАСТЬ XIX. КЛЮЧЕВЫЕ РИСКИ

# 35. Архитектурные риски

### 35.1. GitHub не является специализированным мессенджером

Возможны задержки, API-ограничения и сложности при большом количестве сообщений.

**Решение:** очереди публикации, локальный индекс, восстановление синхронизации.

### 35.2. Комментарии PR не версионируются Git

Коммит сам по себе не позволяет восстановить точное состояние переписки.

**Решение:** неизменяемые snapshots и аудит.

### 35.3. Долгоживущие PR создают сложную Git-топологию

Особенно при многоуровневых Fork.

**Решение:** отделить логическую топологию разговоров от правил Git merge.

### 35.4. Контекст растёт

Агентам становится дорого читать длинную переписку.

**Решение:** Context Package, выбор релевантной истории, сохранение исходных ссылок.

### 35.5. Агенты могут неправильно интерпретировать предыдущие решения

**Решение:** структурированные Decision Objects и подтверждение пользователем.

### 35.6. Расходы на ИИ

Несколько агентов могут создавать большое количество вызовов.

**Решение:** бюджетирование по чату, агенту и рабочей сессии.

### 35.7. Конфиденциальность

Чаты могут содержать приватную информацию.

**Решение:** private-by-default, минимальные разрешения, контролируемая передача контекста.

# ЧАСТЬ XX. ГЛАВНОЕ ПРОДУКТОВОЕ ОТЛИЧИЕ

# 36. Почему это не обычный AI Chat

Обычный чат представляет собой линейную последовательность сообщений.

Chat.0.1.1.0 добавляет три измерения:

**Первое — коллективность.**

Несколько независимых ИИ участвуют в одном обсуждении.

**Второе — ветвление.**

Любая идея может стать самостоятельным исследованием.

**Третье — происхождение.**

Каждый результат связан с историей, которая к нему привела.

Таким образом, продукт объединяет:

**Chat + Git + AI Agents + Decision Management + Knowledge Graph.**

# 37. Итоговое продуктовое определение

**Chat.0.1.1.0 — Git-native платформа коллективного мышления и разработки, позволяющая людям и ИИ совместно вести обсуждения, создавать Fork идей, фиксировать решения и визуально исследовать происхождение результатов.**

Главная ценность:

Не просто сохранить, *что* решили.

А сохранить:

- Почему решили.
- Кто предложил.
- Из какой идеи возникло.
- Какие альтернативы проверили.
- Где изменили направление.
- К каким результатам пришли.

**Главный принцип продукта:**

> У каждой идеи есть источник. У каждого решения — история. У каждого Fork — точка возвращения.
