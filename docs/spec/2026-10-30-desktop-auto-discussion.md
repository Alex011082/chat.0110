# CHAT-002: автоматическое обсуждение в существующих Desktop-сессиях

Статус на 30.10.2026: владелец разрешил локальный транспорт существующих сессий
и доведение сценария до сквозной работы. Подготовлен пилот Claude и конечная
очередь; полная цепочка двух Desktop-сессий не подтверждена. Новые права, расходы,
заменяющий исполнитель, merge и продакшен не разрешены.

## Результат и область

Основной интерфейс — существующий веб-чат CHAT.0110. Владелец включает двух
ранее приглашённых участников: сообщение в веб-чате → существующая сессия Codex
→ один ответ в том же веб-чате → существующая Claude Code в Claude Desktop
→ итог → остановка. Ручная пересылка каждого хода не нужна.

Первое включение ограничено `Alex011082/Y-TNG`, PR #522,
`chat/20261030-pp11`. Другие чаты не включаются. Привязка содержит владельца,
репозиторий, chat_id, точные session_id CHAT.0110, исходные идентификаторы сессий
приложений и поколение включения. Имена моделей и отображаемые названия не служат
идентичностью. Смена процесса требует новой проверки соответствия.

## Что проверено и что ещё нет

- Удалённый `chat0110_pending` уже фильтровал по session_id, но позволял пропустить
  его. Каталог сервера содержал поле, доступный агенту каталог клиента — нет.
  Локальная правка требует непустой session_id в схеме и runtime; RU/EN-примеры
  включают его. Устаревший клиент получает ошибку, а не общую очередь аккаунта.
- Очередь, claim/context/reply, ограниченная цепочка `@@`, поколения включения
  и outbox уже существуют. Обычный MCP-вызов не будит завершивший ход клиент.
- GitHub webhook сейчас сообщает интерфейсу об изменении. Он не превращает
  произвольный новый файл сообщения в задание и не завершает claim.
- API целевого чата при read-only проверке вернул 7 сообщений и событие создания,
  head `e104fd368c590b2887aa3559e150db1f1c3fad17`. Это подтверждает серверную
  выдачу; старое отображение четырёх сообщений в браузере не воспроизведено.
- Метаданные выбранной Claude-сессии связывают её исходный hostSessionId с
  entrypoint `claude-desktop`, версией 2.1.309 и существующим inbox-сокетом 0600.
  Сокет не открывали для отправки, ключи не читали. Подтверждения доставки и
  пробуждения именно этой сессии нет.
- Установленный Codex CLI 0.142.3 поддерживает `app-server proxy` и команду
  `daemon version`. Последняя не обнаружила стандартный control socket.
  Это не проверка всех внутренних транспортов Desktop. Найденный отдельный
  `ipc.sock` не идентифицирован как публичный App Server; его нельзя использовать
  по догадке. Новые daemon/app-server/CLI-сессии не запускались.

## Поддерживаемые направления проверки

[Claude cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
описывает inbox для скриптов/хуков, пробуждение простаивающих сессий и ограничения
входящих сообщений. Для адаптера нужны версия протокола, поддерживаемый payload,
подтверждение доставки и привязка к собственной сессии. Наличие сокета не означает
готовности; настройки inbound могут удержать или отклонить сообщение. Глобально
разрешать входящие сообщения всем сессиям нельзя.

[Codex App Server](https://learn.chatgpt.com/docs/app-server) описывает Unix transport,
thread/read, thread/resume и turn/start. Не установлено, как публично подключиться
к уже работающему Desktop-host выбранной сессии. Запуск другого App Server с той
же историей не считается доказательством управления исходной сессией. Нужны
поддерживаемый endpoint текущей версии и read-only проверка точного thread_id.

Если такое подключение для текущего клиента недоступно, минимальный честный
вариант — ручной старт активного участия через уже существующий MCP с точным
session_id. Он не обеспечивает фоновое пробуждение. Для полного автоматического
результата потребуется поддерживаемая клиентская возможность или обновление
приложения; заменять её мастер-cron, кликами по окнам или новым платным
исполнителем нельзя. Этот предел не объявляется исправленным серверным PR.

## Минимальное расширение в разрешённом объёме

Локальный адаптер слушает задания только двух явно привязанных сессий. Он
доставляет уведомление в исходную сессию приложения, не выполняет модельный
запрос сам. Модель использует существующие take/context/reply; только успешно
записанный reply продвигает цепочку. Автор файла в Git не доказывает полномочий
агента и не заменяет claim. Повторная регистрация не должна автоматически включать
все чаты аккаунта. Токены и локальные capabilities остаются в закрытом хранилище,
в Git и журнале — только безопасные идентификаторы и состояния.

GitHub webhook — подсказка перечитать разрешённую ветку, а не доверенный текст
задания. Сохраняем в SQLite обработанные delivery_id, head/cursor и message_id.
При первом включении фиксируем базовую историю без её повторного исполнения.
Уникальность задания: repo + chat_id + source_message_id + target_session_id +
generation. Получение, запись outbox и сдвиг cursor атомарны; ответы имеют
стабильный answer_id. Перезапуск и повтор webhook не создают новые ходы.

Новые Git-файлы видны в интерфейсе автоматически. Само появление файла не
запускает бесконечное обсуждение: маршрутизация применяется к разрешённому новому
запросу владельца и существующей конечной цепочке, максимум три хода. Будущий
свободный режим обсуждения требует отдельного согласования лимитов. Завершённый
итог, ошибка или ожидание владельца останавливает цепочку. Текст агента не даёт
разрешения на merge, deploy, расходы или расширение доступа.

При неоднозначном результате отправки адаптер сначала сверяет receipt/историю
исходной сессии. Слепой повтор запрещён. Остановка увеличивает generation,
выключает новые доставки и старые ожидающие уведомления; уже выполненный внешний
эффект отменить таким переключателем нельзя.

## Состояния интерфейса

Синхронизация Git показывает применённый head, время успешного чтения и ошибку.
SSE-соединение или heartbeat сами по себе не означают свежую историю.

Участник отдельно показывает: зарегистрирован; ожидает транспорт; проверяет
соединение; готов; задание в очереди; работает; ошибка; офлайн. «Готов» требует
ответа на пробу от точной исходной сессии и живого канала, а не регистрации или
недавнего touch. Кнопка включения до проверки сообщает причину ожидания и не
обещает автоответы. После отключения готовность не сохраняется фиктивно.

## Приёмка и оценка остатка

Локальный адаптер уже разрешён владельцем; расширение прав остаётся отдельным
вопросом. Нужно получить version-matched способ подключения обоих исходных
клиентов без UI и без смены исполнителя. Оценка условная: одна ограниченная
итерация на доказательство подключения; при успехе ещё 2–3 итерации на адаптер,
Git ingress/UI и сквозные проверки. Если публичного endpoint нет, срок полного
результата зависит от клиента; это не задача на одну серверную правку.

Сквозная приёмка на целевом чате: запрос владельца из веба → Codex → один ответ
в вебе → Claude Desktop → итог и остановка, с доказательством исходных thread_id.
Дополнительно: добавленный Git-файл виден без reload; повтор webhook, reconnect,
перезапуск и повтор reply не размножают сообщения/работу; остановка отсекает
старое поколение; потерянный ack не ведёт к слепому повтору; другой чат/аккаунт
не получает задание. Проверка локальных контрактов не заменяет эту приёмку.

Safari, пользовательские окна и вкладки в диагностике не используются.

## Проверенный срез продолжения CHAT-004

Диагностический inbox вызов получил настоящий ответ существующей Claude Desktop
в [PR522](https://github.com/Alex011082/Y-TNG/blob/chat/20261030-pp11/Chat/conversations/20261030-pp11/messages/20261030T200610Z-claude-2w33.md).
Это PASS одного wake, не полной цепочки. Пилотный runner использует тот же inbox,
штатные agent/next/context/complete и существующий gh login. В модели не запускает
никаких других исполнителей. Перед регистрацией требует ack от исходной сессии.
Живая проба helper не получила ack: классификатор Claude отклонил выполнение
внешнего кода. Listener остановился; запрет не обходили. Нужен прямой шаг владельца
в этой Claude-сессии: разрешить проверенный helper для ack/context/reply в пилоте,
без общего ослабления режима разрешений.

Codex: встроенная версия CLI содержит queue, системная — нет. В официальном
исходнике plain queue вызывает start_app_server_for_session_command и без
--resume; ThreadResume отдельный. Этот исходник не объявлен точно совпадающим с
бинарным build. Прямой queue не запускался, потому что shared-host attach не доказан.
Второй путь — неизменённый штатный codex-app-tools через MCP stdio с настоящим
окружением текущего executor. Он завершился ошибкой pipe closed до tools/list.
Ни read целевого thread, ни диагностическая отправка этим путём не подтверждены.
Прямой private pipe и подмена caller metadata не используются.

В реализованной очереди общий срок — 15 минут с создания цепочки; reconnect и
heartbeat его не продлевают. Выключение автоответов отменяет связанные активные
цепочки. Повторное включение ждёт нового запроса владельца, старую цепочку не
возобновляет. complete завершает её раньше; needs_owner останавливает до новой
явной команды. Поздний ответ с прежним claim сохраняется после локальной очистки
и проверки текущих прав GitHub, без продолжения. После отзыва доступа публикация
не выполняется: локальный сохранённый ответ остаётся для сверки владельцем.

Native outbox ограничен тремя попытками только при известном отказе до отправки.
Identity и fingerprint неизменны; SQLite CAS и single-instance lock исключают
двойную отправку. Неопределённый результат не повторяется. Потерянный HTTP complete
восстанавливается из сохранённых text/outcome, максимум три попытки, без нового
prompt модели. Эти лимиты native runner не меняют прежний retry-порядок облачного
ChatGPT callback. Полный E2E и приёмка владельцем остаются открытыми.

Готовность в UI больше не выводится из регистрации/touch. Она учитывает реальный
открытый запрос ожидания транспорта или активную цепочку, а для ChatGPT — подписку.
Native listener начинает такое ожидание только после подтверждённого Desktop ack.
Состояние listener не сохраняется как готовое через перезапуск сервера.

## Исходный механизм уже есть: точный trace

Правый блок «Ссылка для агента» формируется InfoColumn → agentLinkPhrase →
локализованная agentPhrase. Он копирует приглашение прочитать PR и ответить файлом.
Это рабочий Git-путь участия; повторная отправка приглашения не создаёт постоянную
подписку. Текущий экран владельца не проверялся и по старому скриншоту не описывается.

Отдельный существующий путь автоответов: кнопка участника / ConnectAgents →
chat0110_connect → подписка chat0110.turn.ready → cloudTasks → MCP Events outbox →
callback клиента → take/context/reply → файл в Git и chat.updated в веб-ленте.
Для ChatGPT Work этот механизм уже был подтверждён настоящими ответами. Его не
заменяем новым агентом или платным сервисом.

В текущей реализации events/subscribe и parseParams допускают recipient=chatgpt
и подтверждённый webhook клиента. Pump/status/автовыбор cloudTasks также привязаны
к этому получателю. Нет зарегистрированного поддерживаемого callback для выбранных
Codex Desktop и Claude Code Desktop; назвать их chatgpt было бы подменой actor и
не обеспечило бы доставки в нужные сессии. У Claude отдельно доказан настоящий
inbox wake, но запуск helper остановлен классификатором. У Codex ни callback,
ни attach штатного MCP client не подтверждены. Именно эти звенья до wake не замкнуты,
а не сохранение сообщений/PR как таковое.

Владелец выбрал только доставку по событию и отклонил 5-минутный модельный heartbeat.
Native listener ожидает серверную очередь без вызова модели; inbox будит модель
только при конкретном адресованном задании. Это не периодическое поручение модели
проверять PR. Для Codex fallback с модельными проверками не устанавливается.
