# Протокол чата chat.0110

Источник истины для кода — `packages/chat-protocol`.

Репозиторий продукта хранит свои обсуждения у себя. Пока в нём нет годного
`Chat/protocol.json`, действует схема 1 ниже: каталог `chats/`. Подключение
(`chat0110 init` или кнопка «Подключить Chat к проекту») создаёт `Chat/` и
переводит **новые** чаты на схему 2. Старые чаты из `chats/` не переносятся
этим шагом и открываются по прежним ссылкам. Перенос — `chat0110 migrate`
и кнопка «Перенести чаты в Chat».

Схема 2 расходится со спецификацией от 23.10.2026, и приоритет у нового
решения владельца:

- снимок Fork «ветка от коммита родителя» больше не считается достаточным
  для комментариев PR, но код Fork в этом изменении не переписан;
- цепочка `decisions/` и `foldDecisions` остаётся только для схемы 1.
  В подключённом репозитории текст PR — обсуждение, не решение. Новый
  файл решения сервер отклоняет. Уже лежащие решения перенос копирует,
  чтобы история не пропала, и не превращает их в утверждение.

## Схема 2

- Маркер — `Chat/protocol.json` (`schema_version: 2`, `root: "Chat"`).
- Главный документ агентам — `Chat/AGENTS.md`. `Chat/CLAUDE.md` только
  ссылается на него. Уже лежащие файлы, включая `Chat/README.md`, init не
  перезаписывает.
- Паспорт нового чата — `Chat/conversations/<chat_id>/chat.json`.
- Сообщения — `Chat/conversations/<chat_id>/messages/`.
- Коммит разговора в подключённом репозитории может менять только `Chat/**`.
- Каталог не появляется от одного доступа к репозиторию.

## Перенос

`chat0110 migrate` запускается на ветке `chat/<id>`. Кнопка делает то же
для каждого чата репозитория. На ту же ветку ложится новый коммит.

- Копируются паспорт, сообщения и уже лежащие решения. Байты те же.
- История Git не переписывается, force push нет.
- Номер, адрес и комментарии PR не меняются. Тело PR не переписывается:
  чат по-прежнему находится по старому блоку `chat0110`.
- Файлы в `chats/` не удаляются, старый путь в GitHub открывается.
- Повтор ничего не перезаписывает. Другой текст в `Chat/` останавливает
  перенос этого чата.
- Недостающий каркас, включая `Chat/protocol.json`, дописывается. После
  маркера сервер читает чат из `Chat/` и новые сообщения пишет только туда.
- Коммит Fork не трогается. На том коммите нет `protocol.json`, поэтому
  снимок родителя читается из `chats/`.
- Ветка Fork копирует только свой чат, не снимок родителя.
- Чужой `Chat/AGENTS.md` не перезаписывается.

Полный diff старого PR по-прежнему содержит `chats/`: эти файлы добавлены
прежними коммитами. Проверка CI поэтому всё ещё пускает `chats/`. Новые
записи сервера идут только в `Chat/`.

## Схема 1

Источник правил для ещё не подключённых репозиториев — `chats/AGENTS.md`.
Меняешь описание схемы 1 здесь — меняй и там.

## Протокол схемы 1 (schema_version 1)

## Чат

- **chat_id** — `ГГГГММДД-xxxx`, 4 символа `[a-z0-9]`. Регулярка: `^\d{8}-[a-z0-9]{4}$`.
  Не зависит от названия: переименование чата не трогает ни id, ни ветку.
- **Ветка** — `chat/<chat_id>`, создаётся от головы ветки по умолчанию.
- **Паспорт** — `chats/<chat_id>/chat.json`:

  ```json
  {
    "schema_version": 1,
    "chat_id": "20261023-k7q2",
    "title": "RoboChain — захват коробок",
    "created_at": "2026-10-23T10:02:00Z",
    "created_by": "alex011082",
    "parent": null
  }
  ```

  `parent` зарезервирован под Fork (Этап 2): `{chat_id, message_id, commit_sha}`.
- **PR** — из `chat/<chat_id>` в ветку по умолчанию, draft, метка `chat0110`.
  Если draft недоступен (приватное репо на бесплатном плане) — обычный PR с
  префиксом `[chat]` в названии. В теле PR — блок:

  ```markdown
  <!-- chat0110
  chat_id: 20261023-k7q2
  schema_version: 1
  -->
  ```

  Название чата = название PR (без префикса `[chat] `). PR чата никогда не сливается.

## Fork

Fork — новый чат, ответвлённый от сообщения родителя (п. 4 спеки).

- **Точка ветвления** — коммит ветки родителя, на котором чат выглядел как в
  момент выбранного сообщения: для файла — коммит, который его добавил; для
  комментария — последний коммит не позже комментария (`findForkCommit`).
- **Ветка** `chat/<child_id>` создаётся **от этого коммита**. Новые сообщения
  родителя в неё не попадают.
- **Снимок** `chats/<child_id>/context.json` (после подключения —
  `Chat/forks/<child_id>/context.json`) фиксирует всю цепочку предков до их
  точек ветвления: тексты файлов и комментариев PR на этот момент. Дальше
  лента ребёнка читает снимок и не зависит от того, жива ли ветка родителя
  и не правил ли кто комментарий. Старый Fork без снимка собирается из файлов
  на коммитах; в ответе `complete: false` и текст, чего не хватает. Позднее
  сообщение предка в контекст не входит.
- **chat.json** дочернего чата: `parent: {chat_id, message_id, commit_sha, reason?}`.
- **PR** — из `chat/<child_id>` в `chat/<parent_id>` (дифф показывает только
  новый чат), draft, метка `chat0110`. В блоке тела PR — дубль родителя для
  дерева: `parent_chat_id`, `parent_message_id`, `fork_commit_sha`.
- **Агенты** в дочернем чате видят историю родителя файлами
  `chats/<parent_id>/messages/` в своей ветке, а пишут в `chats/<child_id>/messages/`.

## Решения (Этап 5)

Решение — цепочка событий-файлов `chats/<chat_id>/decisions/<stamp>-<author>-<rand>.md`
(тот же формат имени, что у сообщений). Статус не хранится, а вычисляется
сворачиванием событий по времени (`foldDecisions`); история решения — история Git.

Frontmatter события: `id`, `decision` (у `propose` равен `id`), `action`
(`propose | accept | reject | reopen | discuss`), `author`, `created_at`, а у
`propose` ещё `title`, `source_messages` (id через запятую), `from_chat`
(Fork, из которого пришло предложение), `supersedes` (id заменяемого решения).
Тело — обоснование.

Статусы: `proposed → under_discussion → accepted | rejected`, `reopen` → `reopened`.
Принятие решения с `supersedes` переводит старое в `superseded` — оно не удаляется.
`accept`, `reject`, `reopen` от агента остаются в истории с пометкой, но статус
не меняют: последнее слово за человеком (п. 2.3 спеки).

**Предложить родителю** (п. 4.7): из Fork событие `propose` пишется в ветку и
папку решений **родителя** с `from_chat = <fork_id>`. В родителе это карточка
«Предложение из Fork» с действиями «Открыть Fork / Принять / Отклонить / Обсудить».

## Сообщение-файл

Путь: `chats/<chat_id>/messages/<stamp>-<author>-<rand>.md`

- `stamp` — `ГГГГММДДTччммссZ` (UTC);
- `author` — `^[a-z0-9][a-z0-9_-]{0,31}$`: id агента или GitHub-логин человека
  в нижнем регистре;
- `rand` — 4 символа `[a-z0-9]`.

Регулярка имени: `^(\d{8}T\d{6}Z)-([a-z0-9][a-z0-9_-]{0,31})-([a-z0-9]{4})\.md$`.

Frontmatter (YAML, только плоские строки):

| поле | обяз. | смысл |
|---|---|---|
| `id` | да | имя файла без `.md` |
| `author` | да | логический автор |
| `reply_to` | нет | id сообщения |
| `created_at` | нет | ISO 8601 UTC |

Если frontmatter нет или он битый — сообщение всё равно показывается: `id` и
`author` берутся из имени файла, текст — всё содержимое.

## Сообщение-комментарий

Обычный комментарий PR (`issues/:n/comments`). Необязательный блок в конце:

```markdown
<!-- chat0110
id: 20261023T101400Z-codex-m3p8
author: codex
reply_to: 20261023T100300Z-alex011082-q9w1
-->
```

Без блока: `id` = `c<id комментария GitHub>`, `author` — по карте bot-логинов
(`packages/chat-protocol/src/agents.ts`), иначе GitHub-логин в нижнем регистре.
Блок вырезается из показываемого текста.

## Сборка ленты

Источники одного чата:

1. Файлы `chats/<chat_id>/messages/*.md` на голове ветки чата.
2. Коммиты ветки до merge-base с веткой по умолчанию — а у дочернего чата до
   коммита Fork, чтобы коммиты родителя не попадали в его ленту → кто запушил
   каждый файл (`pushed_by`, `commit_sha`). Коммит, который не добавил ни
   одного сообщения, становится событием `push` («Codex запушил: …, N файлов»).
3. Комментарии PR.
4. Ревью PR и комментарии к строкам — вид `review`.
5. PR в ветку чата (`base = chat/<chat_id>`) — событие `agent_pr`; добавленные
   в них файлы-сообщения показываются как сообщения со статусом «не влито».
   PR из ветки `chat/<id>` того же репо — это дочерний чат (Fork), а не ответ
   агента: он показывается ссылкой под сообщением-точкой ветвления.

Живые события: пуш в ветку чата будит и сам чат (`chat.updated`), и список с
деревом (`repo.updated`); PR дочернего чата будит и его, и родителя.

Повторы склеиваются по `id`: файл главнее комментария.

Порядок: по `created_at`; если его нет или он невалиден — по дате коммита
(для комментария — по дате комментария). При равенстве — по `id`.

## Авторство

Логический автор (`author`) и реальный GitHub-актор (`pushed_by`/логин
комментария) хранятся раздельно. Интерфейс показывает актора, если он
отличается: «Claude · запушил alex011082».

отправил ссылку на PR каждому агенту в его приложении.

- Своих PR и комментариев агенты не открывали: путь «PR агента → Принять в

## Защита данных (27.10.2026)

`POST /api/chats/:owner/:repo/:chat/privacy` принимает `{text}` и возвращает
`{text, counts}`: очищенный вариант и количество замен по категориям SECRET,
EMAIL, PHONE, DOCUMENT, CARD, BANK_ACCOUNT, PERSON, ADDRESS. Нужен вход,
свой Origin и доступ к существующему чату; проверка ничего не публикует.

Отправка через HTTP и `chat0110_reply` повторяет обязательную серверную
проверку перед SQLite и GitHub. При сбое — HTTP 503 `privacy_unavailable`
(в MCP — ошибка инструмента), без публикации. Маркеры `[PERSON_1]` и аналоги
сохраняются в тексте; оригиналы и обратимые таблицы не сохраняются.

Существующие записи очищаются в выдаче, история Git остаётся прежней.
Перенос старого чата/merge сообщения из PR с находками останавливается.
Прямой push, вложения и изображения обходят эту текстовую защиту.

Модель: GLiNER multi-v2.1, revision 443d26d654e0324125a96bebd8e796c14ff2efe6,
Apache-2.0. Подготовка: `bash deploy/privacy-setup.sh`; после установки веса
и токенизатор используются offline в существующем systemd-сервисе. При
проверках библиотеки не получают ключи окружения/учётные данные приложения;
ошибки процесса не выводятся в журнал. Python-зависимости из requirements.txt.

Для повторяемой отправки обычного сообщения также передавайте `request_id`:
сервер сохраняет только отпечаток очищенного запроса и стабильный id файла.
Повтор с другим очищенным содержимым или reply_to возвращает 409.

Большие тексты распознаются пакетно. Предел одной проверки модели — 90 с,
таймаут HTTP для API/MCP — 240 с; SSE остаётся без таймаута. На текущем CPU
проверка 59000 искусственных символов заняла 42,4 с после загрузки модели.
Длинный тест модели можно повторить командой `benchmark.py --long`.

Проверенные текстовые поля кешируются в серверной SQLite (`privacy_checked`):
HMAC содержимого + версия политики → зашифрованный очищенный результат.
На неизменившемся содержимом модель повторно не вызывается, включая рестарт.
Очищенная строка также получает собственное подтверждение для следующих
этапов HTTP/MCP. Клиент не может прислать доверенную отметку проверки.
Версия зависит от кода сканера, worker, закреплённой модели и словаря имён ИИ;
при её изменении старые результаты не используются. Оригиналы не сохраняются.
