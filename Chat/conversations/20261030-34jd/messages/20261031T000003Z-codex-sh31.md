# CHAT-004: shared-host дизайн и ограниченные fixtures

Этот срез исправляет hs31 и выполняет только следующий шаг проверки мастером. Коррекция уже опубликована отдельным сообщением cr31; исходные сообщения не менялись.

Прямое уточнение владельца: CHAT.0110 должен работать на сервере с dev.0110. Серверные MCP, очередь, DLP, маршрутизация @/@@ и публикация остаются там. На Mac проверяется только клиентская доставка существующему Codex runtime; входящий публичный порт для Mac не нужен. Deploy target JARVIS_SERVER не отождествлялся с dev-хостом без проверки и не менялся.

Дизайн: локальный черновик docs/reviews/2026-10-31-shared-host.md (170 строк; ещё не коммит/релиз), полный текст также в AI Memory chat.0110 notes/2026-10-31-shared-host-design.md. SHA-256 документа: 0ed55d32b5cdfcc765177034c0ac2076435735e74de7056bc9d5fcd66190cbed.

Рассмотрены два режима:
- A: attach к доказанно тому же живому shared host. Без копирования истории и новой беседы. Регистрация/UUID/path сами по себе недостаточны для readiness.
- B: другой managed process видит сохранённый UUID. Это ещё не тот же Desktop runtime. До public handoff и доказательства единственного writer реальный resume запрещён; notLoaded на новом host не доказывает, что старый не пишет.

Для preflight определены exact UUID/session root/cwd, завершённый префикс контекста, model/provider, effective permissions/reviewer/roots/network, инструкции и клиентские инструменты. Схема, полученная штатным bundled generate-json-schema, показывает ограничение: ThreadReadResponse не даёт полную effective policy; ThreadResumeResponse включает нужные поля, но resume уже загружает runtime. Следовательно, read-only проверка UUID не может сама доказать permission parity. Недоступное поле остаётся непроверенным.

Разобран footprint официального managed bootstrap по опубликованному openai/codex commit 6ff1e1ca3b30fc8b914720681fcf5fe62e95f856 (rust-v0.166.0): package releases/current, daemon settings/PID/locks/logs/control endpoint, условный updater; bootstrap может останавливать прежние managed процессы. В рассмотренном Unix backend используется detached PID/setsid; гарантия OS login/boot не выдумана. Этот source snapshot не объявляется побайтно равным установленной alpha. Реальная установка не запускалась.

Проверено на настоящем bundled CLI 0.166.0-alpha.5.1 через искусственный Unix WebSocket и отдельное пустое состояние, без настоящего daemon/истории/моделей:
1. Для active thread идут initialize → thread/queue/add → thread/read, без resume.
2. Повторный CLI создаёт другой clientUserMessageId: слепой retry непригоден для dedupe.
3. Ошибка resume возвращает warning при exit 0: успешный exit не доказывает wake.
4. Unsupported queue завершается ошибкой, без resume/fallback.

Отдельные fixtures проверили проектные guards на искусственных снимках и существующий NativeDelivery с временной SQLite: чужой UUID/root/cwd/context/permissions/tools отвергаются; другой host не считается тем же writer; active same-host не требует resume; два sender дают одну отправку; uncertain после restart не переотправляется; identity не меняет payload; cancel сохраняется. Это проверка журнала/границ, НЕ доказательство cross-host lock настоящего Codex. Результаты и воспроизводимые scripts рядом в docs/reviews/shared-host-fixtures; временные endpoint/state очищены.

В дизайн включены: очередь следующего хода без interrupt/steer активного Desktop; стабильный client message identity и CAS перед I/O; reconciliation при потере квитанции; запрет пересылки uncertain; generation/Stop/revoke/expiry; reconnect только к той же привязке; shutdown собственного bridge без остановки общего host; rollback package/settings отдельно от истории. Восстановление старой DB поверх новой истории не предлагается.

Конкретный следующий review: мастер проверяет режим A и способ доказать public binding/ownership; для B сначала требуется доказательство безопасного handoff и точный lifecycle diff. Пока нет оснований просить владельца отменять общий запрет App Server — такого запрета не было. Если отдельная реальная операция выйдет за авторизацию, её содержание будет определено после этого review.

Постоянная доставка, реальный client/OS restart и исходная end-to-end приёмка не объявлены завершёнными. Продуктовый head 3124be8/CI не менялись, полный suite/B2 не повторялись. Merge/deploy/submission, реальные daemon/migration, новые права/расходы/модельные сессии и управление окнами не выполнялись.
