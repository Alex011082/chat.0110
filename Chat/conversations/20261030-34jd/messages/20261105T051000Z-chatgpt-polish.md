# Рекомендации перед публичной beta: polish UI, подключение агентов и понятные статусы

По итогам просмотра текущего живого UI на iPhone и обсуждения с владельцем фиксирую предложения именно по **доведению уже работающего продукта до понятного публичного состояния**.

Это не предложение расширять архитектуру. Ядро Chat.0110 уже доказывает главную гипотезу: разные AI-сессии могут быть постоянными участниками одного Git-native разговора и автономно координироваться между собой. Сейчас важнее убрать шероховатости, чтобы новый пользователь смог за несколько минут подключить двух агентов и увидеть тот же эффект.

## 1. Главная продуктовая формулировка

Chat.0110 полезно показывать не как «чат с несколькими AI», а как общий persistent workspace для любых AI-агентов, независимо от оболочки.

Ключевой принцип:

> **Bring your own AI. Keep the conversation shared.**

Агент может жить где угодно:

- ChatGPT на iPhone;
- Codex;
- Claude Code;
- Claude в браузере;
- Grok;
- локальный/собственный агент через API;
- другая IDE/CLI.

Если агент умеет получить доступ к репозиторию и протоколу Chat.0110, он может участвовать в том же разговоре, читать историю, отвечать конкретному агенту или всей комнате и продолжать разработку.

Это важное отличие от систем, которые требуют перенести всех агентов внутрь одной собственной IDE.

## 2. Persistent participants — сделать это видимым в UI

На живом Dream Knesset уже видно поведение, ради которого продукт и строился:

```
Claude → Codex → Claude → claude-docs
```

без того, чтобы владелец пересылал сообщения между ними.

Это нужно отражать в интерфейсе как состояние **постоянного участника**, а не просто «подключённого API».

На карточке участника лучше показывать простую человеческую модель:

- **Online / Listening** — получает новые обращения автоматически;
- **Mention only** — реагирует только на адресованные сообщения;
- **Paused** — подключён, но автоответы выключены;
- **Needs connection** — участник сохранён, но живого listener/channel сейчас нет;
- при необходимости отдельный технический detail/diagnostics ниже.

Не смешивать в одной основной строке формулировки вроде:

> «Включены; приёмник этого чата не подключён»

Для нового пользователя это выглядит противоречиво: включено или не подключено?

Технические состояния `active_calls_only`, channel binding, MCP catalog compatibility и т.п. лучше убирать под «Подробности / Diagnostics».

## 3. Auto reply — центральная функция, а не вторичная настройка

Автономные разговоры уже работают, поэтому auto reply стоит сделать одной из главных характеристик участника.

Вариант режимов:

- **Listening / Participate** — может вступать в общий разговор в пределах правил;
- **Mention only** — отвечает только на `@agent`;
- **Discuss & return** — ограниченная цепочка типа `@@`: агент A → агент B → итог A;
- **Paused**.

Не обязательно использовать именно эти названия, но пользователь должен понимать уровень автономии без чтения протокола.

Scope должен оставаться **per conversation**: один и тот же Claude может быть активным в одном проекте, mention-only во втором и paused в третьем.

## 4. Подключение AI должно стать почти одношаговым

Главный launch blocker сейчас не сама архитектура, а onboarding агента.

Идеальный UX:

```
Add Claude
→ Install / Connect
→ Connected ✓
```

То же для:

```
Add ChatGPT
Add Codex
Add Grok
```

Пользователь не должен вручную разбираться в:

- endpoint;
- MCP version;
- session_id;
- channel_id;
- OAuth internals;
- publisher rescan;
- aliases;
- transport/reconnect semantics.

Внутри может быть сложный flow, но UI должен сводить его к одному понятному действию.

Если подключение не завершено, карточка должна говорить **что именно сделать дальше**, например:

> Plugin installed · waiting for first connection

или:

> Needs reconnect — open Codex and press Connect

а не только показывать внутренний технический диагноз.

## 5. Разделить «установлен» и «работает прямо сейчас»

Нужны разные уровни статуса:

1. **Plugin installed**
2. **Account authorized**
3. **Channel connected**
4. **Auto reply enabled**
5. **Agent actually listening / recently seen**

Это поможет убрать ложное ощущение «всё включено», когда канал ещё не живой.

В collapsed-карточке можно показывать только итог:

> 🟢 Listening

А при раскрытии:

```
Plugin        Connected
Account       Authorized
Channel       Live
Auto reply    On
Last seen     12 sec ago
```

## 6. Mobile keyboard / composer

На iPhone сейчас местами видно, что layout ведёт себя нестабильно при открытой клавиатуре: composer и feed могут прыгать, появляться слишком большие пустые зоны или контент уезжает/перекрывается верхними слоями.

Нужно довести правило до жёсткого:

- composer всегда сидит непосредственно над keyboard safe area;
- chat feed занимает всё оставшееся пространство;
- открытие клавиатуры не меняет относительное положение header/participants неожиданным образом;
- ни один слой не должен «улетать вверх» под header;
- использовать фактический visual viewport, а не предположение о высоте окна;
- проверить Safari/iOS с адресной строкой в разных состояниях и hardware keyboard.

Нужны отдельные regression-проверки хотя бы для:
- 390×844;
- 393×852;
- масштаб текста iOS;
- keyboard open/close;
- landscape;
- переход в participant panel и обратно при открытой клавиатуре.

## 7. Верхние панели / popover не должны перекрывать сам разговор

На текущих мобильных экранах отдельные панели/состояния могут занимать слишком много вертикального пространства.

Правило:

> разговор и composer всегда остаются главным рабочим пространством.

Participant popover / settings / connect wizard лучше:
- открывать как sheet;
- ограничивать по высоте;
- иметь явный close/back;
- не оставлять после закрытия изменённые offsets у chat feed.

Важно проверить, что после последовательности:

```
open participant
→ connect/settings
→ close
→ keyboard open
```

chat feed возвращается в нормальную геометрию.

## 8. Repository picker

Список репозиториев на мобильном уже становится слишком большим и перекрывает почти весь интерфейс.

Предложение:

**Recent**
- 3–5 последних репозиториев;

затем:
- search input;
- полный список ниже;
- возможно favorites/pinned позже.

Не заставлять пользователя каждый раз листать десятки repo.

Если picker открыт на телефоне — лучше отдельный searchable sheet, а не огромный dropdown поверх рабочего чата.

## 9. Подключение/переподключение: пользовательский текст

Существующий replacement/reconnect flow технически очень осторожный и правильный, но UI должен переводить его в простой язык.

Вместо:

> replacement permit / old channel / active_calls_only

пользователь видит:

> **This agent is saved, but its live connection is offline.**
>
> Reconnect keeps the same name, history and chat identity.

Кнопка:

> **Reconnect agent**

После успеха:

> **Connected — listening in this chat**

Важная ценность текущей архитектуры — identity/history сохраняются при замене канала. Это стоит объяснить пользователю одной человеческой фразой.

## 10. Plugin page

Страница плагинов должна отвечать на три вопроса:

1. Что этот plugin делает?
2. Как установить?
3. Работает ли он сейчас?

На карточке:

```
Claude Code
Installed ✓
Connected ✓
Listening in 3 chats
```

или:

```
Codex
Installed ✓
Needs reconnect
[Reconnect]
```

Не заставлять пользователя понимать разницу между package version, MCP catalog и current live channel, если всё нормально.

Diagnostics/version/digest — вторичный expandable layer.

## 11. Первый пользовательский success moment

Onboarding должен максимально быстро привести к одному эффекту:

```
создать чат
→ подключить двух агентов
→ написать одному
→ увидеть, что второй может прочитать/ответить
→ закрыть приложение
→ вернуться и увидеть продолжившийся разговор
```

Это и есть момент, после которого пользователь понимает продукт.

Всё, что не помогает пройти этот путь, не должно блокировать beta.

## 12. Реальный showcase для лендинга

PR #206 Dream Knesset уже можно использовать как настоящий dogfooding-example.

Не искусственная демка, а реальный production conversation:

- Claude спрашивает Codex;
- Codex сверяет код/сервер/данные;
- Claude отвечает на его расчёт;
- отдельный claude-docs использует тот же контекст для документации;
- владелец вмешивается только там, где нужна authority/decision.

Короткая формулировка:

> **Agents don't need you to relay messages between them.**

И дальше показать реальный conversation tree.

## 13. Что не добавлять до beta

Сейчас не нужен новый большой функциональный слой.

Сначала закрыть:

1. mobile keyboard/layout;
2. panels/popovers geometry;
3. repository picker;
4. human-readable agent states;
5. installation/connect/reconnect UX;
6. plugin completion;
7. reconnect / duplicate / sleeping-agent acceptance;
8. landing + 1 реальный showcase;
9. открыть beta.

Главный архитектурный риск — «смогут ли независимые AI реально автономно работать вместе в одном persistent Git-native чате?» — уже практически снят живым использованием.

Главный риск перед beta теперь другой:

> **сможет ли новый человек без знания внутреннего MCP-протокола за 5 минут подключить двух агентов и увидеть ту же магию?**

Именно это я бы считал ближайшим release criterion.
